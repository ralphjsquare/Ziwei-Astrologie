# 解读文字准则

解释文字是本项目最容易出问题的部分：一旦写成“断语”，就可能误导读者。以下准则由 `validateRules` 中的语言检查（`lintText`）和审核流程共同执行。

## 一、每条解释必须能回答三个问题
1. **这句话说的是什么条件？** 触发条件在规则的 `when` 中，只有盘面满足条件才显示。
2. **依据是什么？** 分四级：古籍原文（有语料引文）、流派观点、现代整理、算法结构。没有语料引文的，不得标为古籍原文；“已确认”状态只允许有古籍原文的规则。
3. **审核到哪一步？** 未审核、已审核、已确认、已驳回，全程显示。

## 二、写法
- 用“传统上认为”“倾向于”“常被理解为”等转述语气，说明这是**传统说法**，不是对个人的预言。
- 不使用绝对化、宿命化用语（必定、注定、肯定会、绝对、必然……），不使用恐吓式用语（克夫克妻、短命、血光、灾祸……）。
- 不替读者做决定，不给医疗、投资、婚姻、法律等建议；涉及健康、婚姻的宫位，只说“传统上看这方面”，并提示不能替代专业意见。
- 同一现象各流派说法不同的，如实并列，不选边；不确定的写“待核”。
- 解释要能被普通人看懂：先白话，再折叠出处。不堆砌术语。
- 象征性说法（如十二长生的“死”“绝”）必须说明是比喻。

## 三、不做什么
- 不给“吉凶总分”“匹配度百分比”。
- 不用星曜组合去“判命”：主星入宫的组合说明是按星性与宫位含义机械组合的，标注“模板组合”，只帮助理解。
- 不引入任何没有来源的“秘传”“口诀”。

## 四、上线前的检查清单（每条规则）
- [ ] 触发条件与盘面结构一致（有测试）
- [ ] 语言检查通过（`npm run check:sources`）
- [ ] 来源目录中有对应书目；有语料的已回写引文（`corpus:apply`）
- [ ] 老师审核并在 `review.status` 留痕（`review:import`）
- [ ] 与已有规则没有互相矛盾
