# 紫微斗数 + 八字 交互软件：开发计划（v2）

> 本文件是项目的**唯一规划依据**，同时供人和开发代理（Claude Code / Codex）阅读。
> 修改范围、流派默认值、验收标准，必须先改本文件（或新增 ADR），再改代码。

---

## 0. 目标与非目标

**目标**
1. 输入出生年月日时分（及出生地、性别），得到**准确、可复现**的紫微斗数命盘和八字命盘。
2. 支持紫微流年（大限/流年/流月）、八字大运/流年/流月，支持两人**合盘**（紫微合盘、八字合婚）。
3. 提供**解盘**：本命、流年、合盘，每条解释有**古籍出处 + 白话解释**，并标明依据等级。
4. 提供紫微与八字的**并列呼应对照**。
5. 本地运行，可存档；先做网页应用，核心保持平台无关，未来可包成桌面软件。
6. 提供**审核文档导出接口**，用于本人审核和与专业老师交流。

**非目标**
- 不做综合"评分"或"匹配度百分比"（没有依据，见 §7.3）。
- 不做联网账号、云同步、支付。
- 不在软件内做讨论功能；审核通过导出文档在软件外进行。
- 不做择日、姓名学、盲派全量神煞（列入后续扩展）。

## 1. 已确认的决策

| # | 议题 | 决策 |

## 2. 核心原则（开发时不得违反）

1. **算法与解释分离**：引擎只输出结构化数据，不含任何解读文字。
2. **确定性**：排盘是纯函数。引擎内**禁止**使用 `Date.now()`、`Math.random()`、本地时区、`toLocaleString` 等环境依赖。同样输入（含选项）→ 逐字节相同输出。
3. **整数优先**：排盘用整数运算。仅节气时刻等必须用浮点的地方，集中在 `calendar-core`，输出取整到分钟并有测试保护。
4. **规则数据化**：安星表、四化表、格局条件、解释文本都是数据文件，不散落在代码里。
5. **每条规则必须有出处**（见 §6）。没有出处的规则，构建失败。
6. **禁止凭记忆生成古籍原文**：古籍原文只能来自导入的**数字化语料**（附来源 URL、版本、校验和），不得由开发代理"默写"。这是防止杜撰古籍的红线。
7. **流派可插拔**：所有存在分歧的地方做成选项，默认值有 ADR 依据。
8. **两个引擎互不依赖**：紫微、八字只依赖 `calendar-core`。呼应层只读两个引擎的输出，不反向影响。

**技术选型（建议，M0 中以 ADR 确认）**
- TypeScript（strict）、pnpm workspace、Vitest、fast-check（属性测试）。
- 前端：React + Vite，命盘用 SVG 绘制；样式不依赖平台特性。
- 桌面化预备：所有 I/O 走接口（`StorageAdapter`、`Clock` 由调用方注入），前端与引擎之间只传纯数据。
- 历法库候选：`tyme4ts` / `lunar-javascript`（6tail，节气与农历）；交叉验证候选：`iztro`（紫微）。**都只作为对照或适配层来源，最终以我们自己的测试集和天文台数据裁决**。
- 规则数据用 JSON/YAML + JSON Schema（或 zod）校验。

## 4. 计算引擎规格

### 4.1 输入与输出

```ts
BirthInput = {
  year, month, day, hour, minute,     // 公历，出生地当地时间
  calendar: 'solar' | 'lunar',        // 可直接输入农历（含闰月标记）
  gender: 'M' | 'F',
  place?: { tz: string /* IANA */, longitude?: number },
}
Options = {
  trueSolarTime: boolean,             // 默认 false
  ziHourRule: 'split' | 'lateZiNextDay' | 'sameDay',   // 见 4.3
  leapMonthRule: 'midMonth' | 'currentMonth' | 'nextMonth',
  ziweiSchool: 'sanhe' | 'feixing' | ...,              // 默认 sanhe
  baziMethod: 'ziping' | 'ditiansui' | ...,            // 默认 ziping
}
Chart = { ..., meta: { engineVersion, rulesVersion, options, inputHash, outputHash } }
```

- 引擎输出的每个结论都携带**算法步骤记录**（如"命宫=寅起正月顺数至生月逆数至生时"），便于和古籍对照与审核。

### 4.2 calendar-core（共享，最关键）

| 能力 | 要求 |
|---|---|
| 支持范围 | 1900–2100（超出范围明确报错，不静默出错） |
| 公历↔农历 | 含闰月、大小月；与**香港天文台 1901–2100 公布数据**逐日核对 |
| 二十四节气 | 天文算法计算，精确到分钟；与天文台/权威历表核对；节气日前后 ±1 日专项测试 |
| 干支 | 年（立春界与正月初一界**两套并存，分别命名**）、月（节令界）、日（儒略日推算，锚点有测试）、时（五鼠遁） |
| 纳音 | 六十甲子纳音表（数据文件，附出处） |
| 时区 / 夏令时 | 使用 IANA tz 数据库；覆盖中国 1986–1991 夏令时、历史时区变化 |
| 真太阳时 | 经度差 + 均时差，可开关，默认关；开启后输出校正明细 |
| 输出 | 同时给出「农历口径」和「节气口径」两套时间，字段名区分，**禁止混用** |

### 4.3 子时与日界（选项，默认需 ADR）
- `split`：23:00–24:00 为晚子时，日柱按次日，但时辰仍为子（传统较多采用）。
- `lateZiNextDay`：23:00 起整体算次日。
- `sameDay`：23:00–24:00 仍算当日。
- 引擎在盘面元数据中**明确记录**所选规则；界面在出生于 23:00–01:00 时弹出提示。

### 4.4 ziwei-engine（默认三合派）
步骤（每一步都是纯函数，单独测试）：
1. 由农历生月、生时定**命宫、身宫**。
2. 十二宫天干（五虎遁）。
3. 由命宫干支纳音定**五行局**。
4. 由局数与农历生日定**紫微星**位置（含商余法），推**紫微星系**六星与**天府星系**八星（天府与紫微成对称关系）。
5. 辅星、煞星、杂曜：左辅、右弼、文昌、文曲、天魁、天钺、禄存、擎羊、陀罗、火星、铃星、地空、地劫、天马、红鸾、天喜等（按《全书》安星诀，逐星有规则条目）。
6. **四化**（按年干）。四化表在若干天干上存在版本差异，做成**可选版本表**，默认取《全书》通行版本并 ADR 记录。
7. 大限（由五行局定起运岁数，阴阳男女定顺逆）、小限、流年、流月、流日（可选）。
8. 庙旺利陷（按《全书》表）。

### 4.5 bazi-engine（默认子平法）
1. 四柱：年（立春）、月（节令）、日、时。
2. 藏干（含本气、中气、余气及权重，权重表来源需 ADR 记录，因流派有差异）。
3. 十神、十二长生、纳音、空亡。
4. 大运：阳男阴女顺排，阴男阳女逆排；起运岁数按"三天折一年、一日折四个月、一时辰折十天"，精确算法作为选项，默认与主流软件一致并 ADR 记录。
5. 流年、流月、太岁与四柱的刑冲合害关系。
6. 旺衰、格局、用神：**子平法为默认**（《子平真诠》），调候参《穷通宝鉴》；**《滴天髓》等备选方法通过 `schools/` 插件输出，与默认结果并列，不覆盖默认**。
7. 神煞：仅收入有明确古籍出处的少量神煞，其余暂不做。

### 4.6 准确性保障
- **黄金测试集**：紫微、八字各不少于 200 盘，分类覆盖：闰月、子时、立春/节气前后、月末、1900/2100 两端、夏令时期间、真太阳时开/关。来源：权威书籍案例、Rodden 评级高的名人盘、与多个成熟软件交叉一致的盘。每个用例记录来源与核对人。
- **交叉验证**：与 2 个以上独立实现比对，任何差异必须查到古籍依据裁决，写入 ADR，不得"改到一致"了事。
- **属性测试**：例如十二宫恰有一命宫；紫微与天府对称；节气单调递增；农历↔公历往返一致；同输入多次结果哈希相同。
- **快照测试**：盘面输出固化；改动引擎导致快照变化，CI 失败，必须显式更新并说明理由。
- **跨环境一致**：在 Node 与浏览器（Playwright + Chromium）各跑同一测试集，结果哈希必须一致。
- **版本化**：每份盘面带 `engineVersion`；存档重开时重算，哈希不一致则提示（见 §8）。

## 5. 流年盘与合盘

**流年**
- 紫微：本命 + 大限 + 流年 + 流月三层叠加，含流年四化。
- 八字：原局 + 大运 + 流年 + 流月，含与原局的刑冲合害。

**合盘**
- 紫微合盘（默认：三合派宫位与主星对照；可选：飞星派四化互飞）。
- 八字合婚（日柱、年柱纳音、五行互补、十神关系等，按《三命通会》《渊海子平》等有出处的方法）。
- **古籍中没有成熟的合盘体系**，凡属现代流派或现代整理，一律标注 `confidence: modern`，不冒充古籍。
- 输出为**并列对照**，不给出综合分数。

## 6. 解读系统与出处规范

### 6.1 规则数据格式

```yaml
id: ziwei.star.ziwei.ming
condition: { star: 紫微, palace: 命宫 }
classical:
  - quote: "……"                # 必须来自 corpus，禁止手写
    source: { book: 紫微斗数全书, chapter: 诸星问答论, edition: "…", corpusRef: "corpus:zw-quanshu#p123" }
plain: "通俗解释……"
confidence: classical | school | modern     # 依据等级
school: sanhe
review: { status: draft | reviewed | approved, reviewer: null, date: null, note: null }
```

- `confidence`：`classical` 古籍原文直接支持；`school` 某流派观点；`modern` 现代整理。
- **构建校验**（`tools/check-sources`）：无出处、出处在 corpus 中找不到、`classical` 等级却没有原文引用，均失败。
- 白话解释与古籍原文**分开存放、分开展示**，白话不得冒充原文。

### 6.2 三层展示
1. 白话解释（默认展开）。
2. 古籍原文 + 出处（可折叠）。
3. 依据等级与审核状态标签（`未审核 / 已审核 / 已确认`）。

### 6.3 解读范围
- 紫微：十二宫、十四主星、辅煞星、四化、格局（紫府同宫、杀破狼、机月同梁等）、大限流年。
- 八字：十神、旺衰、格局、用神、大运流年。
- 合盘：见 §5。
- 软件内附免责声明：传统文化研究与参考，不构成医疗、投资、婚姻等决定的依据。

### 6.4 审核导出接口（决策 6）
- CLI：`pnpm review:export --scope ziwei|bazi|cross|all --status draft|reviewed|all --format md|html|json|csv`
- 界面：设置页"导出审核文档"按钮，调用同一接口。
- 导出内容：规则 ID、触发条件、古籍原文、出处、白话解释、依据等级、当前审核状态、审核意见留白列。
- 另可导出**"样例盘 + 全部解读"**，便于老师针对具体命盘评审。
- 回写：`pnpm review:import <file>` 读取审核意见（CSV/JSON）更新 `review` 字段，保留修改历史。
- 软件内**不做讨论功能**。

## 7. 呼应对照（紫微 × 八字）

### 7.1 三类对照，分别标注依据强度
1. **结构性共通（可精确计算）**：五行局↔纳音、年干四化↔干支、大限↔大运、流年干支。`confidence: structural`，可完整测试。
2. **主题对照（现代整理）**：事业（官禄宫 ↔ 官杀/食伤）、财（财帛宫 ↔ 财星）、婚姻（夫妻宫 ↔ 配偶宫/财官）、健康、六亲等。映射表放在数据文件中，标 `confidence: modern`，与古籍原文分开。
3. **时间叠合**：同一年份并列显示大限流年与大运流年，标出"两边均提示变动"的年份，**不打分**。

### 7.2 实现约束
- `cross-ref` 只读两个引擎的输出；任何一个引擎单独运行不受影响。
- 两个系统结论相反时，如实并列，标注"两套传统的说法不同"，不做仲裁。

### 7.3 关于"互相印证"的说明（写入软件）
两套系统输入的是**同一组出生数据**，因此它们"一致"**不构成独立证据**，不能据此认为结论更可靠。界面必须显示这条说明，因此不提供综合评分。

## 8. 存档（本地）

- `StorageAdapter` 接口：`list / get / put / delete / exportAll / importAll`。
- 网页适配器：IndexedDB；桌面适配器（未来）：本地文件。
- 存档记录：出生输入、全部选项、`engineVersion`、`rulesVersion`、`outputHash`、备注、创建时间。
- **不存派生结果作为唯一来源**：打开存档时用输入重新计算；若与 `outputHash` 不一致（如引擎升级、规则更新），提示用户并显示差异，不静默覆盖。
- 导出/导入：单文件 JSON（带 schema 版本号和迁移函数），用户可自行备份。
- 数据不上传；界面明确说明数据只在本机。

## 9. 界面（apps/web）

- 输入页：公历/农历、出生地、性别、选项（真太阳时、流派、子时规则等，带简短说明）。
- 命盘页：紫微 4×4 宫格（SVG）、八字四柱表、大运/大限时间轴；点击星曜/干支弹出解释（白话 → 原文 → 出处）。
- 流年页：选择年份，叠加视图。
- 合盘页：两人并列。
- 对照页：呼应对照（三类分栏）。
- 存档页：列表、打开、导出、导入。
- 设置页：流派、审核状态显示开关、导出审核文档。
- 要求：手机宽度可用、深色模式、可打印命盘、无联网依赖（可离线）。
- 未审核的规则默认可见，但**带明显"未审核"标签**；可在设置中改为只显示已审核。

## 11. 里程碑与验收

| 里程碑 | 内容 | 验收标准 |

## 12. 开发代理（Claude Code / Codex）工作约定

同样内容会写入根目录 `AGENTS.md`。

1. **开工前**先读本文件和相关 ADR；任务范围以里程碑为界，不越界。
2. **一次只做一个里程碑的一个子任务**，每个子任务：实现 + 测试 + 文档，独立提交。
3. **不确定就写 ADR，不要猜**：流派分歧、默认值、表数据来源，任何拿不准的地方，停下来列出选项和依据，交给人裁决。
4. **绝不编造古籍原文或出处**。原文只能来自 `packages/corpus`；找不到就把规则标为 `confidence: modern` 或留空并标 `review.status: draft`，绝不虚构引用。
5. **不改测试来迁就代码**。黄金测试与快照变化，必须说明原因并由人确认。
6. 引擎包内禁止环境依赖（`Date.now`、`Math.random`、本地时区、DOM、Node 专有 API），由 lint 规则强制。
7. 提交信息使用约定式格式（如 `feat(ziwei-engine): 紫微星定位`），一个提交一件事。
8. **完成的定义（DoD）**：类型检查通过、相关测试通过、`check-sources` 通过、文档已更新、变更记录已写。
9. 每次交付时汇报：做了什么、测试结果、**未完成或有疑问的点**（如实说，包括失败的测试）。

**给代理的任务模板**
```
里程碑：Mx
任务：……
输入/依赖：……（引用本文件章节、ADR 编号）
验收：……（对应 §11 与 §10）
禁止：……（如不得修改黄金测试）
```

## 14. 主要风险与对策

| 风险 | 对策 |
|---|---|
| 历法口径混用（农历年 vs 立春年） | 两套字段分开命名，类型层面区分，测试覆盖 |
| 节气时刻误差 | 天文算法 + 天文台数据逐日核对 |
| 黄金测试数据难找 | 多软件交叉验证 + 权威案例；每例记录来源 |
| 古籍版本差异 | 每条规则记录 edition；差异进 ADR，不静默取舍 |
| 开发代理杜撰古籍原文 | 原文只能来自 corpus；`check-sources` 强制校验 |
| 范围膨胀（流派、神煞） | 默认只做主流；其余走插件，按里程碑排期 |
| 两系统结论冲突造成困惑 | 只并列，不仲裁，不打分，界面附说明 |
| 审核瓶颈 | 审核导出接口 + 审核状态标签，未审核也可用但明确标注 |
| 桌面化时返工 | 引擎纯函数化、I/O 适配器化，从 M0 起强制 |
