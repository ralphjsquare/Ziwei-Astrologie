## 1. 本版目标

交付一个“计算可信、默认流派可用、结果可追溯”的本地网页应用。v1 首先证明完整纵向链路：

> 出生数据输入 → 历法转换 → 紫微/八字排盘 → 基础时间层 → 最小解释集 → 本地存档 → 审核导出。

### 1.1 核心 v1 纳入范围

- 支持 1901–2100；1900 暂不承诺，除非补充独立权威数据源。
- 公历/农历输入、闰月、节气、干支、纳音、IANA 时区和中国历史夏令时。
- 真太阳时开关；校正前后时间和跨时辰/跨日结果可见。
- 紫微默认三合派：十二宫、十四主星、约定清单内的辅煞星、四化、大限、流年、流月。
- 八字默认子平计算层：四柱、藏干、十神、十二长生、纳音、空亡、大运、流年、流月及刑冲合害。
- 旺衰、格局、用神在 v1 中输出“规则候选 + 依据”，不宣称唯一答案。
- 最小解释集：优先覆盖十四主星十二宫和八字基础概念；所有未审核内容显示状态。
- 最小网页 UI：输入、命盘、时间层、存档、设置/导出。
- 本地 IndexedDB 存档；JSON 导入导出；Markdown/JSON 审核导出。
- Node 与浏览器跨环境测试；关键边界测试；确定性哈希。
- 紫微与八字仅做结构性并列，不做综合分数。

### 1.2 延后到 v1.1 或以后

- 飞星派、钦天四化、《滴天髓》等完整流派插件。
- 流日、流时。
- 完整紫微合盘和八字合婚。
- 现代主题“互相印证”规则库。
- 全量辅煞杂曜、全量神煞和所有格局。
- 400 个经专家逐一确认的黄金盘；v1 先完成覆盖矩阵驱动的较小集合。
- 大规模古籍 OCR、现代点校本打包和付费语料授权。
- Tauri/Electron 桌面安装包。
- DOCX/PDF 审核导出；v1 只要求 Markdown/JSON，可选 CSV。

### 1.3 明确非目标

- 不做科学有效性或人生预测准确性的承诺。
- 不做吉凶总分、匹配度百分比。
- 不做账号、云同步、支付、社区讨论。
- 不允许模型根据记忆生成古籍原文。

## 2. Claude Sonnet 5.5 预算模型

### 2.1 计费基准

本计划暂按 Claude Sonnet 5.5 的公开标准价计算：

- 未缓存输入：$2 / 百万 token
- 5 分钟缓存写入：$2.5 / 百万 token
- 缓存读取：$0.20 / 百万 token
- 输出：$10 / 百万 token

价格来源：[Anthropic — Claude Sonnet 5.5](https://www.anthropic.com/claude-sonnet-5-5)

开始项目及每个重要里程碑前必须重新核对价格；若价格变化，以较保守者更新本表。

计算公式：

```text
费用 = 2 × 未缓存输入(M)
     + 2.5 × 缓存写入(M)
     + 0.20 × 缓存读取(M)
     + 10 × 输出(M)
```

### 2.2 建议 token 信封

这不是必须用完的额度，而是成本规划上限：

| 类别 | 规划 token | 预计费用 |
|---|---:|---:|
| 未缓存输入 | 8.0M | $16 |
| 缓存写入 | 4.0M | $10 |
| 缓存读取 | 50.0M | $10 |
| 输出 | 3.5M | $35 |
| 定价波动、重试、长上下文及误差储备 | — | $14 |
| **硬上限** | — | **$85** |

若缓存无法稳定命中，不得继续按照 50M 缓存读取的假设工作。应缩短上下文、减少重复读取或进一步缩小范围。

### 2.3 分阶段美元额度

| 阶段 | 交付重点 | 上限 | 累计上限 |
|---|---|---:|---:|
| B0 | 仓库、ADR、schema、预算记账 | $5 | $5 |

| B6 | 存档、哈希、审核导出 | $5 | $58 |

### 2.4 预算警戒线

- `$0–$67.99`：正常开发，但仍需逐任务记账。

## 4. 核心技术约束

### 4.1 正确性分层

- `calendar-conformance`：历法与权威历表的一致性。
- `school-conformance`：排盘符合明确版本的流派规则。
- `regression-stability`：相同版本和输入产生相同输出。
- `interpretation-traceability`：解释有可定位来源和审核状态。

禁止用“多个软件算得一样”代替权威依据。外部软件只用于发现差异；差异必须通过 ADR 裁决。

### 4.2 哈希

至少使用三个哈希：

```ts
calculationHash // 规范化后的纯排盘数据，不含本字段
rulesHash       // 参与解释的规则内容哈希
artifactHash    // 完整导出物哈希
```

必须规定规范化 JSON、键排序、Unicode、浮点取整和排除字段。`outputHash` 不得自引用。

### 4.3 存档

- 输入和选项是权威来源。
- 同时保存旧计算结果快照作为非权威缓存。
- 升级后用旧快照和新结果生成差异。
- 只保存旧哈希而不保存旧快照时，不得声称能够展示差异。

### 4.4 出处与审核

```ts
evidenceType: 'classical' | 'school' | 'modern' | 'structural'
reviewStatus: 'draft' | 'reviewed' | 'approved' | 'rejected'
```

- 所有类型都必须有来源；`structural` 可引用算法规格或 ADR。
- 古籍原文只能从已导入 corpus 引用。
- 现代点校、注释、翻译和数字数据库必须单独记录授权或许可。
- 审核记录使用追加历史，不覆盖旧记录。

### 4.5 CLI 与网页

CLI 和网页调用同一个平台无关的领域服务函数；不得让浏览器直接调用 Node CLI。

| # | 缺口 | 影响 | 建议处理（B0 内完成） |

#### R2（G2）古籍语料：只用公版

用户裁决：使用公版。落实标准：

1. **只收原典本身**：《紫微斗数全书》（传统题陈希夷，本项目不断言作者，只记录所用版本）、《渊海子平》、《三命通会》、《子平真诠》、《穷通宝鉴》。《滴天髓》属 v1.1。
2. **不收现代点校本、注释本、白话译本**（这些有版权），除非取得书面许可。
3. **数字化文本的许可要单独核对**：原典是公版，不代表某个网站的录入、校勘和整理也可以随意使用；有的站点要求署名或相同方式共享。B0-1 逐一读取来源站点的条款并记录，**不凭记忆判断**；条款不明确的来源不入库。
4. 每段入库文本必须带：书名、篇章、版本或刻本说明、来源 URL、获取日期、许可说明、SHA-256。
5. 只引用规则所需的短段落，不整本入库。
6. 找不到公版数字文本的规则，`evidenceType` 标 `modern` 或 `structural`，**不写引文**。

#### R3（G3）时辰与节气标准

你的想法是“至少按整点区分时辰”。我的标准是：**时辰按整点，节气按分钟**，两者不矛盾。

- **时辰**：以整点为界，23:00 起子时，其后每 2 小时一个时辰（01:00 丑、03:00 寅……）。输入精确到分钟，不含秒。恰好落在边界的时刻归后一个时辰（01:00 整属丑时）。子时早晚按 D04。
- **节气必须精确到分钟，不能只到整点**：例如某年立春在 14:37，14:10 出生和 14:50 出生同属未时，但月柱不同。只按整点会把其中一个算错。
- **计算与比较**：用天文算法求太阳视黄经每 15° 的时刻，内部以 UTC 整秒保存，对外显示到分钟。出生时刻换算为 UTC 后，**大于或等于**节令时刻即进入新月（含等号）。
- **精度**：与参照来源相差 ≤ 60 秒算通过；超出的进例外清单，由 ADR 裁决。
- **边界警示**（两级）：出生当天有节令交接 → `termOnSameDay: true`；出生时刻与节令时刻相差 ≤ 2 分钟 → `nearTermBoundary: true`。界面提示“临近节气交接，建议核对出生时间”。
- **参照来源**：至少两个独立来源。（a）官方公布的节气时刻，如香港天文台或紫金山天文台的资料；B0-1 先核实其覆盖 1901–2100 与数据格式，**核实前不写成事实**。（b）我们另行实现的独立天文算法，与引擎所用实现不同。三方（引擎、官方、独立算法）互相比对。
- **时区**：官方节气时刻按北京时间公布；出生地钟表时间按 IANA 历史规则换算为 UTC。1970 年前中国部分时期的时区规则不完整，界面提示“早期出生时间的时区为近似”。
- **真太阳时（开启时）**：只修正时辰和日柱的判定；节令比较使用绝对时刻，不受影响。这是默认做法，B0 用边界表确认后写入 ADR。

#### R4（G4）黄金盘：说明与方案

**黄金盘是什么**：事先有确凿“标准答案”的测试命盘。软件算完与标准答案比，不一致就说明有错。

**难点**：标准答案从哪来。如果让软件自己算一遍再当答案，它永远“正确”，测试就没意义。这在软件测试里叫“预言问题”（oracle problem）。

**最佳实践**：能穷举的层面全部穷举，只把人工核对留给整盘。分四层：

| 层 | 测什么 | 标准答案来源 | 规模 | 你的工时 |
|---|---|---|---|---|
| L1 历法 | 公农历、闰月、节气、日干支 | 官方历表；日干支用固定锚点加连续性 | 1901–2100 每一天，自动 | 无 |
| L2 安星表 | 命宫、五行局、紫微星位、四化等有限表 | 《紫微斗数全书》安星诀表格，录入为独立的“查表实现”，与算法引擎逐格比对 | 全枚举：如命宫 12 月 × 12 时 = 144 格，紫微星位 5 局 × 30 日 = 150 格，四化 10 干 | 极少 |
| L3 整盘 | 端到端 | 每系统 60 盘：**20 盘**由确认人按安星诀手工逐步核对签字；**40 盘**由至少 2 个独立成熟实现与本引擎三方一致，有差异走 ADR，以古籍为准裁决 | 60 + 60 | 约 6–8 小时（20 + 20 盘） |
| L4 性质 | 不变量、蜕变关系 | 数学与规则性质，如紫微与天府对称、节气单调递增 | 自动 | 无 |

**取样**：出生数据用**合成的边界矩阵**（等价类 + 边界值 + 成对组合），而不是名人盘。原因：名人出生时间的准确性无法独立确认，还涉及隐私。名人盘仅在有高可信出生时间时作演示，不计入黄金盘。

**记录**：每个用例带 `oracle: { type, source, verifiedBy, date }`。**`oracle` 不得为本引擎自身输出。**

**预算**：D06 的 60 + 60 不变；L1、L2 是脚本化的穷举，成本很低，包含在 B1–B3 内。若超支，先削减 L3 中“双实现一致”的 40 盘。

**最佳实践出处**（请在 B0 核对原文后写入 ADR；此处为我所知的文献，未逐条联网核实）：
- 预言问题：E. T. Barr 等，《The Oracle Problem in Software Testing: A Survey》，IEEE Transactions on Software Engineering，2015。
- 差分测试：W. M. McKeeman，《Differential Testing for Software》，Digital Technical Journal，1998。
- 蜕变测试：T. Y. Chen 等，《Metamorphic Testing: A Review of Challenges and Opportunities》，ACM Computing Surveys，2018。
- 性质测试：K. Claessen、J. Hughes，《QuickCheck: A Lightweight Tool for Random Testing of Haskell Programs》，ICFP，2000。
- 组合测试：D. R. Kuhn 等，《Practical Combinatorial Testing》，NIST SP 800-142，2010。
- 边界值与等价类：ISTQB 测试基础大纲。

#### R6（G6）缓存策略：怎样多命中缓存

**先说原理**：每一轮对话都会把整个上下文重新读一遍。所以费用大致正比于“轮数 × 上下文大小”。两个杠杆：**让前缀稳定，提高命中；让上下文小，少读**。缓存按前缀匹配，前面任何一处改动，后面全部失效。

| # | 做法 | 目的 |
|---|---|---|
| 1 | **稳定前缀**：`AGENTS.md`（≤ 约 1500 token，只放规则和指针）+ 冻结的计划 + ADR 索引。冻结后不改 | 每次会话开头的大块内容都能命中 |
| 2 | **易变内容外置**：成本台账迁出到 `docs/LEDGER.md`，任务卡放 `docs/tasks/`，只在任务开始和结束各读写一次。B0-1 把第 7 节台账迁出 | 台账每个任务都要改，放在计划文件里会让缓存反复失效 |
| 3 | **一个里程碑内连续工作**：不清空会话、不换模型、不改思考强度和工具集，这些都会使前缀失效 | 避免重复付缓存写入 |
| 4 | **攒审核点**：需要你审核的事项攒到里程碑末尾一次给出，而不是每个子任务都停 | 缓存有时效（通常 5 分钟；1 小时缓存需另行核价），你回来时常已过期 |
| 5 | **少轮次、大步骤**：一次写完整个子任务，再一次性跑测试；不做“改一行跑一次” | 轮数直接决定读取次数 |
| 6 | **控制工具输出体积**：测试用安静模式，只在失败时输出前若干行；大表和规则库用脚本生成，不在对话中打印；读文件用检索和片段 | 进入上下文的输出会被之后每一轮重复读取 |
| 7 | **不用子代理和并行代理** | 各自冷启动，不共享缓存 |
| 8 | **实测核对**：B0 结束和每个里程碑结束时报告命中率 = 缓存读取 ÷（缓存读取 + 缓存写入 + 未缓存输入） | 用数据判断，不靠感觉 |

**目标**：命中率 ≥ 85%。预算信封隐含的命中率约 80.6%（50 ÷ 62），所以达到 85% 就有余量。低于 70% 就排查：前缀里有无时间戳或乱序 JSON、工具集是否变动、会话是否被频繁打断。

**说明**：我无法事先承诺能省多少，以 B0 的实测为准。省下的额度归入储备，不用来加功能。
